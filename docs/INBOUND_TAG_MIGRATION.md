# Переименование тегов inbound: предварительная подготовка

В списке внутренних сквадов Remnawave показывает технический `tag` inbound,
а не отображаемый `remark` Host. При изменении тега Panel 3.4.7 считает inbound
удалённым и создаёт новый UUID. Связи Host обнуляются, связи Node и Internal
Squad удаляются каскадно. Обычный откат Config Profile не вернёт прежние UUID.

`inbound_tag_plan.py` — **только автономный планировщик**: читает локальный JSON
и показывает предполагаемые соответствия тегов именам Hosts, а также затронутые
UUID Hosts, Nodes и Squads. Он не подключается к API и ничего не применяет.
Входной объект содержит массивы `profiles`, `hosts`, `nodes`, `squads` в форме
ответов API; достаточно метаданных профилей с inbound UUID и tag. Подготовьте
файл с правами 0600 в закрытом каталоге и не публикуйте конфигурации или секреты.

```bash
python3 inbound_tag_plan.py /root/private/snapshot.json
```

План отклоняет неодинаковые имена нескольких Hosts одного inbound и глобальные
коллизии тегов. Xray 26.10.21 для Windows принял синтетический конфиг с emoji в
теге и ссылкой `inboundTag` при `xray run -test`; серверный Xray и рабочие
профили таким тестом не проверены. Это необходимо проверить на изолированном
стенде с фактической версией. Если у
разных хостов одинаковые названия или теги используются правилами маршрутизации,
нужна дополнительная проверка и явное разрешение конфликтов.

Для реальной миграции ещё нужны: приватный снимок полных конфигураций, сверка
всех ссылок в routing и templates, проверка Xray, отдельный журнал с обработкой
неопределённого ответа API, восстановление привязок по новым UUID, проверка
подписок и клиентов, восстановление служебного состояния установщика и испытание
отказов на отдельном стенде. Существующий `--restore` установщика не является
откатом такой миграции. Этот файл и планировщик не реализуют применение или откат.
